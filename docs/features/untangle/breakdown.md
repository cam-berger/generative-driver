# Breakdown: separate the driver tool from the benchmark

For the owner, who is moving the benchmark to a repository of its own and will evaluate the tool from outside. Today the tool and the benchmark import each other, so the benchmark cannot be lifted out. This Run pulls them apart in place, until they are two installable packages that only share this repository, and it marks every legacy benchmark item for the deletion that follows the move.

## Out

- Deleting the benchmark. That is a later step with its own go-ahead from the owner. One part of it comes earlier, by the owner's decision of 2026-11-18: a benchmark test or document that is not relevant to the benchmark as it now stands, or is outdated, is deleted in Features 10 and 11 and does not move. Each Spec names what it deletes.
- Any change in behaviour, with nine exceptions the owner has decided:
  - Benchmark runs and suites are started from the benchmark's own command. From Feature 09 on the tool's command line and MCP server no longer offer them.
  - The two legacy cases, the old tq9 and the physical BME280, can no longer be run, from Feature 04 on. The benchmark then has no case on real hardware until one is rebuilt.
  - The tool no longer judges the fresh worker's mission during a run, from Feature 05 on. It keeps recording the worker's calls and the readings after them, and the client judges the mission after the run and reports it in its verdict.
  - The records a client sends and reads, the verdict record and the device descriptor, are put in the tool's own terms in Feature 06.
  - Four names that say `benchmark` in the tool are put in the tool's terms in Feature 06: the worker tool `benchmark_package_execute`, the schemas `benchmark-capabilities/2` and `benchmark-ground-evidence/3`, and the subfolder `benchmark/` of a run, where the tool keeps its own records. The owner decided this on 2026-11-16.
  - The tool's interface gains four things for any client in Feature 07, at version 3: `status` finds a run by the request id the client gave it, `result` gives back the request a run was started with, a client can mark a run sealed so that it no longer resumes, and on a supplied run a given `executor_config` is the whole configuration. The bench harness needs them to keep a suite's bookkeeping itself. The owner decided this on 2026-11-16.
  - The run report is the benchmark's, from Feature 08 on. Its code moves to the benchmark, the tool gets no report of its own, and the command `generative-driver report` keeps working until Feature 09 gives it to the benchmark's own command. In the same Feature the tool stops knowing the bench home, so the bench harness alone refuses a replay candidate that lies in it; `result` loses `benchmark_summary`, which only the benchmark's check of reports of the earlier protocol read; the tool's one status text that says `Benchmark` is put in the tool's terms; and the interface, at version 4, says what a client may import, which of the tool's records on disk a client on the same machine may read, and what a client may add and remove there: files of its own in a run's folder, saved replay candidates in the home, and the files of a run that has stopped and is sealed. The owner decided on 2026-11-17 that the report is the benchmark's, and that what the benchmark reads and keeps in the tool's home is written down in the interface and not moved.
  - The benchmark has no MCP tools from Feature 09 on. It is run from a command line, as benchmarks usually are. The seven MCP tools that started a trial and started, followed, cancelled and resumed a suite are removed, so a chat client can no longer do that.
  - The benchmark's command is `firmware-bench` from Feature 09 on, and its package is renamed `firmware_bench` in Feature 12.

  The change to the records edits grading code, so it changes every grader identity and voids every admission from Feature 06 on, and the rename does so again. No generated set is registered, and the hand-made cases are due to be requalified in any case.
- Keeping old records readable. On 2026-11-15 the owner decided to move past them: runs, sealed evidence and reports recorded before Feature 06 need not be readable after it, and new records come from later runs. In the same way, a suite the service stored before Feature 07 is not carried over to the bench harness's store: it is neither read nor resumed after it.
- Fixes to the benchmark, and the 13 notes in `.scratch/benchmark-review/`. Where a Feature must choose between what benchmark runs do today and a tool change the benchmark has not adopted, it keeps what they do today and says so.
- Windows and Python 3.11 stay supported for the tool. While the benchmark is still here, the hosted tests keep running it on both as well.
- The generator volume and the private repository. No session of this Run opens either. Test devices stay hand-written.

The facts for Feature 09 showed three things its line had not settled. The owner decided them on 2026-11-18.

- The benchmark's command takes the name `firmware-bench` already in Feature 09, so that the documents and the tests change once. The owner said on 2026-11-18 that firmware bench is the repository the benchmark is going to: generative-driver is the toolkit and the workflow, and firmware bench evaluates it.
- The benchmark is driven from a command line only. The service started the bench harness for one reason: on Windows an MCP client's child processes end when the client closes, so the benchmark's MCP tools could not start a harness there themselves. The owner first chose that those tools refuse on Windows. The same day the owner chose that the benchmark has no MCP tools at all: they are removed and get no server of their own, and no special case for Windows remains.
- Neither the tool's command line nor its MCP server has ever posted a verdict. The way to accept one verdict from an outside grader is the service's call `record_evaluation`, which the interface lists. It stays, and no command is added for it.

The owner also said on 2026-11-18 that the benchmark's own side need not keep what is there today: it may be shaped like a typical benchmark. The rule against a change in behaviour binds the tool. A Spec that changes the benchmark's side on this ground says what it changes.

On 2026-11-18 the facts for Feature 10 showed that its line asked for more than one Spec can hold. Everything left on the deletion list waited on it: 57 test files that test the tool and the benchmark together, the benchmark's code and resources, and about 130 benchmark passages in 25 documents that stay. The owner decided four things that day.

- Feature 10 is split in two. One Feature is for the tests: it untangles them and moves them. One is for the documents: it rewords them and moves them. Two-packages follows as Feature 12.
- The benchmark gets one folder at the root, `firmware-bench/`. Its tests and documents move there, and in Feature 12 its package and its build file. The tool's `tests/` and `docs/` stay where they are. Copying the benchmark out is then copying that folder.
- Only what is relevant moves. The owner's words: "only if they are relevant documents and tests. If they are not, or outdated in any way, delete them". So a benchmark test or document that describes a past state, or that only holds a passing state of this Run in place, is deleted and not moved. Each Spec names every file it deletes, so that its Approval covers the deletion.
- About 125 tests of the tool's own behaviour run only on the benchmark's cases and devices. The 41 that run on the tool's own fixtures join the tool's tests in Feature 10. The others need the bench harness's device and stay with the benchmark's tests. The Spec of Feature 10 names what the tool then tests only from there.
