# Benchmark baseline

Status: ready-for-agent

Approved by the user on 2026-10-30.

Build a scorecard and a strong baseline of today's main, then grow the benchmark with a device generator, so later systems, starting with the parked learning loop, can be compared on functional equivalence with numbers that hold up. Codex is the only runtime in scope; Goose is out. The learning loop is parked in [its tabletop](../learning-loop/spec.md).

## Decisions

1. **A pass is equivalence.** A trial passes when the evaluator grades its frozen driver equivalent, as the suite report already counts it. Fresh-reuse success and the equivalent-and-reused rate are separate columns; accepted stages are a workflow diagnostic. A trial that emits no driver fails. The corpus report's rule that success needs equivalence, fresh reuse and six accepted stages ([corpus.py](../../src/generative_driver/benchmark_support/corpus.py)) changes to match.
2. **The pass rate divides by graded trials.** Pass rate is passes / (passes + failures), printed on one line with the unknown, fault and planned counts, for example "7/9 pass, 1 unknown, 2 faults, 12 planned". An unknown is a completed grade with no failed step and at least one undecided step; today's yes/no checks never produce one. A fault is a host or operator problem, or missing evidence, that the system did not cause (decision 20). The suite report's all-planned denominator ([suite_reporting.py](../../src/generative_driver/benchmark_support/suite_reporting.py)) changes to match; the corpus report already divides this way.
3. **The baseline can show a 15-point improvement in pass rate.** That needs about 121–170 graded trials per system (two-sided 5% test, 80% power, from a 50–70% starting rate), fewer when both systems run the same devices. At the 2026-10-27 rate of about 1.6M tokens per trial, that is 190–270M tokens per system, so cost per trial constrains the generator. The trials go mostly to distinct generated devices, with difficulty set so today's main passes about half. My call, open to review: one trial per device per system, both systems on the same devices, so about 150 generated devices.
4. **Scoring devices form a fixed sealed set.** The scoring set is generated once and the baseline runs on it once. Only aggregate scorecards leave the bench harness, never one scoring trial's details. Development uses a separate development set from the same generator. Each later system runs the same scoring set and is compared device by device with the stored baseline. Every comparison also runs a small fresh batch as a leak check; a clearly better score on the scoring set than on fresh devices means the set leaked, and replacing it needs a new baseline. Sealing is a working rule backed by file separation, not access control.
5. **The scoring set covers three framings over UART.** Text lines (like the parameter store and the corpus's SCPI, G-code and ASCII interfaces), binary frames with length and checksum (like Modbus RTU and the inertial sensor's packets) and register access (numbered register reads and writes). Each device draws one framing and a random state machine, about 50 devices per framing. The generator writes each device's `application.c` and reuses the existing Cortex-M, Arm GNU Toolchain 14.2, Renode and sealing path ([asset_build.py](../../src/generative_driver/benchmark_support/asset_build.py)). USB, networking and timed streaming wait for their backends.
6. **The baseline pins main after the effect-label fix.** Branch `claude/angry-morse-e784f5` (three commits on `41469aa`) merges through its own pull request before pinning. The executor points at a fixed copy of Codex CLI `0.164.0-alpha.11.1`, taken out of the self-updating `ChatGPT.app`, and every trial records the version it ran; the `codex` on `PATH` is an unrelated program. Model `gpt-6.1-sol` with reasoning effort set explicitly to `medium`. Limits stay at 10,800 seconds per trial, at most two repairs and one active trial.
7. **Generated devices are graded at every step.** The generator writes hidden sequences that start from a verified reset, walk the public mission's tasks and together exercise every transition of the device's state machine. At each step the grader compares the driver's answer (a value, a refusal or no reply) and the device state, read from memory at addresses in the encrypted answer key, with the reference; a step passes only when both match. Each driver result is classified as a value, a refusal, no reply or an error (decision 19). A step whose state cannot be read is unknown, not a failure.
8. **Generated missions state effects only.** A mission gives task names, input names and types, output names with units, one sentence per task saying what the application wants, and the fresh-reuse objective. Valid ranges, refusal conditions, framing, reply formats and the mapping onto firmware commands stay hidden for the system to recover from the firmware. Hidden sequences include out-of-range values, so passing on the device's refusals is graded. Today's missions, such as the [parameter store's](../../src/generative_driver/resources/bench/missions/parameter-store-v1.json), also state preconditions; they stay as they are.
9. **Difficulty is a five-level ladder.** About 30 scoring devices per level, 10 per framing. Each level raises six knobs together: state (modes and transactions), refusal rules and how many depend on state, composite tasks that need several firmware commands in order, hidden triggers that appear only after a repeat count or past a threshold, value encoding (scaled, signed or packed values and checksums), and binary obfuscation (optimisation level, string visibility). A pilot (decision 23) checks that the ladder runs from mostly passing to mostly failing for the pinned system. Pass rates are reported per level as well as overall.
10. **Generated devices register by set.** One code-owned registration per generated set (for example `generated-scoring-v1`, `generated-development-v1`) pins the hash of a set manifest listing each device's image, mission and answer-key hashes. Each device is otherwise a case. This amends ADR 0001; see [ADR 0003](../../docs/adr/0003-generated-devices-register-by-set.md).
11. **References run on every device; mutants run on a sample.** The generator writes two distinct reference drivers and about five mutants per device: at least wrong scale, constant output and wrong state, as [calibration.py](../../src/generative_driver/benchmark_support/calibration.py) requires today, plus framing-specific ones. Both references must pass every device's hidden sequences, which shows that device's firmware and answer key agree. Mutants run on two devices per level and framing (30 devices) to show the hidden sequences catch wrong drivers. That is about 550 native runs for about 200 devices instead of about 1,400. Each set is qualified once, unattended, with its own password; the first runs are timed before a full set is qualified.
12. **The scorecard reads retained records only.** Nothing new is recorded by the system under test, so measuring cannot change the pinned system and a stored baseline can be rescored. Sources: evaluator evidence (outcome, pass rate, step accuracy), configurator events and worker records (wall and worker time per stage, managed calls by tool, repairs, attempts), Codex transcripts (shell commands, file edits, MCP calls, tokens), runtime transcripts (device exchanges, writes, refusals, resets) and the fresh-reuse worker's report against the grade (claim agreement). A finished run on this machine kept all of these in 12 MB, so about 150 trials need about 2 GB, sealed in the answer vault for the scoring set (decision 21).
13. **Systems are compared through a shared scoring set.** Two systems may be compared when both ran the same admitted scoring set under the same evaluator revision and limits, whatever their protocols. The comparison names every changed dimension and labels more than one a combined change, reports each device as passed by both, neither, only the new system or only the baseline, applies McNemar's test to the differing devices and carries its leak check. Reports outside a scoring set stay separate series. This reverses the protocol refusal in [benchmark.py](../../src/generative_driver/benchmark.py) for scoring-set reports; see [ADR 0004](../../docs/adr/0004-compare-systems-through-a-scoring-set.md).
14. **Today's four admitted cases stay as an anchor.** `tq9-v2`, `sampled-sensor-v1`, `parameter-store-v1` and the upstream `zephyr-modbus-v1` run three trials each with the pinned system (12 trials, about 19M tokens), reported apart from the scoring set and never pooled into its pass rate or comparisons. They keep the only real firmware in the baseline and continuity with earlier studies. They are requalified on the pinned revision first, as the [verification record](../../docs/verification.md) requires before the next model study.
15. **Workers see only a generated device's UART, for now.** No instrument observation exposes a generated device's state; the grader's memory reads stay evaluator-private, so named state cannot reveal what the mission hides. The anchor cases keep their instruments. New modalities, such as a debugger-like instrument or another transport, are welcome later as new sets or a changed comparison dimension.
16. **The generator lives in a private repository.** Its own repository and tests sit outside this checkout, the installed package and run folders, as today's synthetic authoring sources do. Only its outputs enter the benchmark: images, missions, encrypted answer keys and set manifests. This repository keeps the generic set adapter, which learns a device's design only by decrypting its answer key; its public tests use hand-written fixture devices, never generator output. Placement alone does not stop a worker that searches the disk, since workers are not read-isolated. See [ADR 0005](../../docs/adr/0005-keep-the-device-generator-private.md).
17. **The answer vault and generator volume stay unmounted while workers run.** A suite's bench harness reads each set's password once at start, keeps it in memory and starts its first trial only after the answer vault and the generator volume (decision 22) are unmounted, so the generator, passwords and unlocked answer keys are encrypted at rest while workers run. Generation, qualification and resuming a stopped suite mount them briefly; a resumed suite waits for the unmount the same way. As a second layer, the scorecard flags any worker command in the Codex transcripts that touches the vault or generator paths; a flagged trial is an integrity fault and is not graded. This changes the bench harness, which is evaluator code, not the pinned system; today it rereads password files when grading ([harness.py](../../src/generative_driver/benchmark_support/harness.py)).
18. **Anyone on the project may read the generator.** People and agents developing the system under test may read the generator's repository; workers in trials still may not (16, 17). Tuning to the generator's style is an accepted risk. The anchor's real firmware, and later an unblocked upstream lineage, are the only check on it, and the scorecard states that limitation.
19. **A refusal counts whoever makes it.** Every driver result is a value, a refusal, no reply or an error. A refusal matches a reference refusal whether the device sent it or the driver declined before sending, as long as the device state is unchanged; its reason is graded only when the mission lists it as an output. No reply matches only a reference silence; an error never matches. Bounds tighter than the device's still fail, because the reference accepts those values. Today the grader records an input outside the driver's declared bounds as a mapping failure before the package runs (`bind_task` in [capabilities.py](../../src/generative_driver/benchmark_support/capabilities.py)); that becomes a refusal.
20. **Running out of budget is a failure.** A spent budget and any stop the system causes itself are failures; only host and operator problems and missing evidence are faults. Today a spent budget is recorded as an operator stop (`_runtime_stop` in [configurator.py](../../src/generative_driver/configurator.py)) and every stop blocks the suite (`child_disposition` in [suites.py](../../src/generative_driver/benchmark_support/suites.py)). The scoring suite moves past a faulted slot and reruns that device once with a fresh trial at the end, recording the replacement; a device still faulted after its rerun leaves the paired comparison and is listed.
21. **Graded scoring trials are sealed in the answer vault.** Once a scoring trial is graded, the harness moves its run folder into the answer vault, encrypted, and leaves a stub, so later workers cannot find a baseline driver for the same firmware and developers see no per-trial details. Scoring suites show aggregates only, and the scorecard runs only with the vault mounted and no workers running. This is an exception to AGENTS.md's rule that the configurator owns durable runs; see [ADR 0006](../../docs/adr/0006-seal-graded-scoring-trials.md).
22. **The generator has its own encrypted volume.** Project members mount the generator volume for development and generation. The answer vault keeps passwords, answer keys, sealed trials and each set's secret seed, so reading the generator never reveals a scoring device. Neither is mounted while workers run. This replaces decision 17's single vault.
23. **A 20-trial pilot and a 350M-token ceiling.** The pilot runs four development devices per level, about 32M tokens. The ladder is kept when level 1 passes at least three of four and level 5 at most one of four; otherwise it is adjusted once and the pilot rerun. Pilot, anchor and baseline together stay under 350M tokens; if trials cost more than planned, the scoring set shrinks toward 120 devices first. Defects that stop today's main from running at all on UART-only devices are fixed and recorded before pinning; anything that only lowers quality is measured, not fixed.

## Settled from the builder check

- **The grader's identity covers grading code only.** Decision 13 needs a later system to be comparable with the baseline, so the identity that admission and comparison check covers the grader's own code and the scoring set's pins, never the system under test's code (configurator, stage adapters, runtime, toolkit, package template) or the list of registered sets. Today `evaluator_revision` ([snapshots.py](../../src/generative_driver/benchmark_support/snapshots.py)) and `calibration_identity()` ([reference_calibration.py](../../src/generative_driver/benchmark_support/reference_calibration.py)) cover all of these. Narrowing them is [issue 01](../benchmark-lifecycle/issues/01-scope-qualification-closure.md), and it must land before the scoring set is admitted, because the baseline's identity is fixed when it runs.
- **Generated sets never enter the public repository.** The GitHub repository is public and today's cases ship in the wheel, so committing a generated set would publish it. My call: each set is an encrypted bundle outside the repository (images, missions, answer keys and manifest); a suite's harness decrypts one device's inputs into its trial when the trial starts; a resolver serves the anchors' in-repository assets and the external sets together. Development sets stay unpublished too.
- **Fresh reuse leaves the verdict, as decision 1 says.** This conflicts with the accepted design: for `interface-package/2`, the evaluator's `final_record` puts `generated_mcp_reuse` and `fresh_worker_mission` checks inside the verdict ([evaluator.py](../../src/generative_driver/benchmark_support/evaluator.py)). The verdict drops them, and the scorecard also computes the old joint verdict for the anchors from their records, for continuity with earlier studies. My call: on a generated device, fresh-reuse success is judged by the evaluator's private memory reads after the reuse stage against the state the reference predicts for the objective, since there is no instrument.
- **Raw images at every level.** Renode cases give workers a raw `firmware.bin`, so stripping symbols would change nothing. My call: every level ships a raw image, and the knob becomes string visibility: command names appear as plain strings at easy levels and are encoded at hard ones.
- **tq9-v2 should still unlock.** The 2026-10-29 study could not open an older tq9-v2 ciphertext, but the vault notes list a version-5 password and a 2026-10-23 unlock for tq9-v2, which is registered as version 5. Requalification confirms it; if it fails, the anchor uses tq9-v3, as that study did. My call.

## Constraints

- Develop through the benchmark run/score/compare seam: observe each behavior test fail, implement, then observe it pass ([AGENTS.md](../../AGENTS.md)).
- Code in this repository supports native macOS and Windows 11+, with argument-array process launches, no hardcoded user paths and outputs outside installed resources.
- The bench harness holds passwords; the configurator and workers never receive passwords, their paths or plaintext answers.
- The user runs every qualification with their passwords; agents prepare the commands and say when.
- Model runs (pilot, anchor, baseline) launch only when the user assigns them. Never silently retry an uncertain write.

## My calls, open to review

- One trial per device per system (decision 3).
- Development set: two devices per level and framing (30), the 20 pilot devices among them.
- Leak check: one fresh device per level and framing (15) per comparison, run by the new system only; it can expose only a large gap.
- The legacy cases (`tq9`, `bme280`, `setup-smoke`) stay out of the baseline, unchanged.
- One password per generated set.

## Build order

1. Merge `claude/angry-morse-e784f5` through its own pull request.
2. Narrow the grader's identity to grading code ([issue 01](../benchmark-lifecycle/issues/01-scope-qualification-closure.md)).
3. Scorecard in this repository: pass, failure, unknown and fault with the graded pass rate in suite and corpus reports (1, 2, 20), a scoring suite that moves past faulted slots and reruns each once (20), the records-only metrics (12), the comparison rule in `compare` (13) and the transcript audit (17). Tested with scripted and replay runs, at no model cost.
4. Set adapter in this repository: set registration and manifest pinning (10), the step grader with refusal classification (7, 19), UART-only devices (15) and the resolver for external encrypted sets, tested with hand-written fixture devices. Fresh reuse leaves the verdict.
5. Bench harness: read each password once, start trials only after both volumes are unmounted (17), decrypt one device's inputs per trial and seal each graded scoring trial in the answer vault (21).
6. Private generator in its own encrypted volume (16, 22): three framings, five levels, effects-only missions, hidden sequences, two references and about five mutants per device, built through the existing Arm GNU Toolchain and Renode path.
7. Development set: generate it; the user qualifies it; the pilot's 20 trials run once the user assigns them; adjust the ladder (23).
8. Pin the system (6); the user requalifies the anchor.
9. Scoring set: generate it; the user qualifies it; the baseline's about 150 scoring and 12 anchor trials run once the user assigns them, within the 350M-token ceiling (23).
10. Store the baseline and publish its aggregate scorecard.

## Open risks

- The pinned system's ground stage normally compares meanings with instrument readings; on a UART-only device it should record semantic uncertainty and continue, which is unchecked; a defect that stops it running is fixed before pinning (15, 23).
- Qualification time and tokens per generated-device trial are unmeasured (3, 11).
- The Codex CLI inside `ChatGPT.app` updates itself until the fixed copy is in place (6).
- The transcript audit catches only reads visible in commands (17).
- Generator-style tuning by developers is accepted; only the anchor checks it (18).

## Left to the builder

The answer-key schema for generated devices, the set manifest format, the count and length of hidden sequences, the mutant list beyond the three core ones, how the two references differ, the paths the audit flags and the scorecard's file formats.
