# Benchmark lifecycle integration

Status: claimed

The user requires one coherent benchmark structure for adding cases, selecting or excluding them, executing the existing pipeline and interpreting the result. Acceptance checks must follow observable functionality, explicit compatibility or safety/integrity requirements.

## Scope

- One trusted case-registration declaration, lazy family loading and explicit mission dispatch.
- Full-catalog immutable selection with reasons and unchanged coverage slots.
- Operator-only authenticated qualification check before model execution.
- Existing suite owner, bounded repair, six stages and package-only fresh reuse.
- Separate graded success, selected coverage and full-catalog coverage.
- Local Markdown tracker and default triage labels, as selected by the user.
- Primary-source comparison with SWE-bench, Harbor/Terminal-Bench and Tau-bench.
- Native monitor controls and observations correlated with their own replies, retaining private wire evidence without redispatch.

## Acceptance

Exercise the public CLI from outside the checkout: list, plan, include, exclude, check, start, status/resume and report. A fresh reader must find the add/bootstrap/qualify/activate/promote/retire steps in the normal docs. Preserve old plans, all blocked/excluded slots, credential separation and failure attribution.

Observe behavioral regression tests fail before implementing changes. Run the repository tests, qualify the current native evaluator and execute an actual agent trial through all six stages. Authenticate and regrade its saved encrypted evidence. Preserve failures and interventions; do not convert missing evidence into a model failure.
