# Generative Driver: accepted design

This brief records the public repository and the six-stage workflow confirmed on 3 October 2026. Implementation follows the agreed public test seams using one failing behavior test and its implementation at a time.

## Agreed outcome

Developers can install the toolchain, skills and workflow through documented Goose or Codex setup, connect supported hardware, state an objective and inspect the resulting package and evidence. The core runs natively on macOS and Windows 11 or later. Optional analysis and benchmark dependencies may use containers.

Goose and Codex provide the developer-facing interface. A local background configurator owns the workflow, controls the orchestrating agent and stage agents, manages their configured runtime connections and device access, and retains progress independently of the UI. The first release launches configured agent runtimes rather than implementing a provider API agent loop. Codex and Goose execution adapters share the same stage contract; the runtime, provider and model identities are recorded separately.

The configurator owns six roles: acquire, interpret, probe, ground, emit and reuse. One stage is active per run. Agents make stage decisions and report their work; deterministic checks control whether reports become accepted handoffs. A run ends when a fresh agent uses the emitted driver to perform the requested device functions and independent checks accept that behavior.

## Architecture

```mermaid
flowchart TD
    U[Goose, Codex or CLI] --> M[Configurator interface]
    M --> C[Background run controller]
    C --> A[Orchestrating and stage agents]
    A --> T[Scoped toolchain tools]
    T --> D[Selected device or emulator]
    C --> E[Accepted handoffs and evidence]
    E --> P[Portable device package]
    B[Benchmark runner] --> M
    E --> V[Independent evaluator]
    G[Groundtruth evidence] --> V
```

The installed package provides the configurator, tools, portable runtime, model contracts and generic skills. Run state and outputs live in user-selected storage outside the installed package. A small CLI and MCP interface support setup checks, configuration, starting a run, reading status and evidence, supplying a requested observation, cancellation and checked recovery. Calls return a durable run identifier; reconnecting observes the same run.

The configurator records assignments, worker reports, checked handoffs and routing separately. Accepted artifacts are immutable and referenced by hashes. A worker exit code or a claim of completion cannot substitute for required check results. Model defects can return to interpret; host and operator faults route to the relevant correction without teaching the interpreter incorrect device facts.

Device bindings belong to the operator. Managed workers share exclusive device ownership through the configurator. Operations retain explicit effect grants and bounded execution. Cancellation prevents further dispatch, records the result of any outstanding operation and preserves uncertainty after interrupted writes. Recovery never silently repeats an uncertain physical action. For an owned emulator before final grading, the configurator may dispose of the old process, verify a distinct replacement against independent startup observations, and use the remaining interpretation repair budget. Every unresolved effectful dispatch must have its own trusted completed model-failure evidence; unknown, host or operator failures block that route. Failed commands and historical uncertainty remain in evidence. Cancellation, lost ownership, failed replacement verification and exhausted budgets retain the dispatch block.

Blind interpret receives only its prepared description and generic kit. Fresh reuse receives only the emitted package, objective and permitted operating information. Each execution records the restrictions actually enforced. The developer-facing chat's history, benchmark answer keys and previous candidate outputs are excluded from these worker inputs.

Each benchmark uses one stable firmware image. Diagnostic observations may support bounded interpretation repairs before emission. Frozen final checks qualify the submitted package after fresh worker use; their failure is terminal.

## Public repository

The repository is `generative-driver`, with Python package `src/generative_driver/`. Original code is licensed under Apache-2.0. Existing reusable code is extracted selectively from the current working tree, including relevant uncommitted improvements. The source research repository and its frozen records are preserved.

```text
README.md                 purpose, supported paths and first successful run
src/generative_driver/       configurator, tools, runtime, packaged generic resources
plugins/                  Codex plugin and Goose installation assets
skills/                   canonical generic workflow and stage instructions
docs/                     architecture, macOS/Windows and UI setup, support matrix
tests/                    behavior tests at the agreed public seams
bench/README.md           prerequisites, run/score/compare instructions and metrics
bench/cases/              versioned benchmark inputs and execution manifests
bench/groundtruth/        independent evidence, reference vectors and evaluator keys
bench/evaluators/         scoring outside candidate access
.github/workflows/        macOS and Windows installation and behavior checks
```

The installed agent resources contain generic tools and skills. The benchmark's device sources, answers, scorers and historical outputs remain evaluator-side assets. Public evidence is selected for each worked example and retains provenance and limitations. Device recordings, vendor assets and historical Git contents are not copied wholesale. Third-party notices accompany any included third-party material.

Codex receives plugin metadata, MCP wiring and skills. Goose receives a recipe and skills with its documented MCP setup. Both connect to the same configurator. Setup documentation walks from the relevant UI through runtime selection, optional dependency checks, installation smoke, and the first supported hardware or benchmark run. A plugin installation does not by itself establish that optional native drivers or analysis tools are installed.

## Benchmark profiles

| Profile | Execution | Evidence and purpose |
|---|---|---|
| Installation check | Scripted fixture and recorded replay, no paid inference or hardware | Exercises installed CLI/MCP, workflow records, package emission and independent package replay. Labelled as setup smoke, excluded from model-performance scores. |
| Emulated STM32 families | Actual configured agents against owned TQ9, sampled-sensor and parameter-store firmware in Renode | Independent observations score readings, effects and state transitions, followed by package-only use by a fresh agent. |
| Physical BME280 sensor | Optional real sensor and supported adapter, with operator-supplied reference measurements | Exercises actual transport and fresh reuse against physical observations. Its score remains distinguishable from emulation and replay. |

Protocol checks and semantic correctness receive separate evidence. A valid frame or executable package can still return the wrong value or perform the wrong effect. Fresh reuse must establish that a new agent can operate the package from its published interface.

Each groundtruth case includes source/build provenance, pinned input hashes, hand-auditable vectors, an independent oracle or primary documentation, observations from the reference channel, expected stage outcomes and known incorrect outputs that the evaluator must reject. The BME280 evidence establishes stable-environment agreement with operator references within their supplied uncertainty; it does not establish absolute sensor calibration.

A benchmark can execute completely and report that the model failed its task. Reports distinguish execution status, accepted workflow state and evaluator verdict. Overall task success requires all six acceptance gates, the fresh worker mission and independent final behavior; averaging stage scores cannot erase a failed required gate. Blocked, failed, unrun and inapplicable stages remain explicit.

Record case and evaluator versions, toolchain revision, agent runtime/version, provider/model/settings, skill revision, attempt limits, environment, generated model/package hashes, stage scores, false capability claims, elapsed time, tool calls, reported usage, retries and human input. Missing usage remains unknown. Comparing different agent runtimes is a comparison of complete systems. A comparison that changes several variables labels that fact.

Provide a one-run development mode and a repeat mode for baselines. Repeated outcomes remain visible; summaries include success counts and median time/usage. The default suite runs three firmware families with three fresh repetitions each: nine trials. Inference execution and its configured limits are explicit, separate from installation smoke.

## Approved TDD seams

These four interfaces were confirmed before new tests were written. Existing useful behavior tests are retained and adapted through these interfaces.

| Seam | Observable behavior |
|---|---|
| Installed CLI and MCP | A built package installs in a clean environment, works outside its checkout including paths with spaces, exposes the configurator, completes setup smoke and reports unavailable optional dependencies. |
| Configurator and worker execution | Real runtime adapters receive the correct stage context/tools. Assignments advance only after checked reports. Duplicate starts, stale results and altered inputs cannot advance twice. UI disconnect/reconnect, cancellation and process recovery preserve one consistent run and fresh reuse. |
| Device runtime and emitted package | Bindings and effect grants are checked before I/O. Managed operations have exclusive access. A relocated package describes, replays and executes through its public interface; tampering is rejected; uncertain writes are not retried automatically. |
| Benchmark run, score and compare | Independent known-good and deliberately wrong submissions receive expected verdicts. All six roles are observable in the agent benchmark. Replay is labelled, missing data stays missing, incompatible comparisons are identified, and fresh use of the frozen package is required for success. |

Tests exercise the actual installed CLI, stdio MCP protocol, process boundaries and package interface where those are the seam. External devices, provider execution and clocks may have controlled substitutes for deterministic contract tests. Substitute workers and replay never count as actual model benchmark results. Native macOS and Windows runners validate the portable release; optional backend and physical validation are reported separately.

## Final decisions

The design and four public test seams were confirmed. Groundtruth uses password-encrypted evaluator storage, with artifact and input hashes. The evaluator keeps the password outside candidate prompts, environments and workspaces. Hashes establish integrity and provenance; this is password-based separation, not an operating-system sandbox.

Scores measure functional equivalence: the same supported inputs must produce the expected outputs and effects within the declared tolerances. Candidate code need not resemble reference code.

Native reference qualification and scripted release checks establish evaluator and software behavior. Model-performance trials select an actual runtime/model and explicit budgets separately. Their failures and unavailable measurements remain in the reports.

## Transaction evaluation amendment — 2026-10-05

Parameter-store update discards pending edits in either bank, commits only the requested cell, preserves other committed cells, advances generation once and ends idle. Both diagnostic and final contracts require named idle update, pending same-bank update, pending different-bank update, stage/commit, stage/abort and rejection scenarios, with complete ending state observations. Rejection requires captured bytes matching an independently authenticated complete-response witness in the evaluator contract; candidate receive boundaries and reject prefixes do not establish completeness. Equivalent request encodings remain valid. The three emulated cases advance to case/evaluator version 5 with fresh native qualification; prior model experiments retain their frozen version 3 meaning. [Verification](verification.md) records software, native and installed evidence separately.

## Assistive protocol amendment — 2026-10-07

New runs record `protocol: "assistive/1"`. For these runs this amendment supersedes the checked stage progression above: "deterministic checks control whether reports become accepted handoffs", "assignments advance only after checked reports", diagnostic observations as repair input, the six acceptance gates as the success criterion, the terminal frozen-final failure, and a configurator that unlocks truth to own the emulator. Earlier runs keep their recorded meaning; resuming one is refused, and assistive results are a new series that is not compared with gated results.

The configurator coordinates; for an emulated benchmark, a bench harness plays the operator:

```mermaid
flowchart LR
    H["Bench harness: operator, holds the password"] --> P["Device provider and emulator"]
    H -->|"device descriptor, admission hash, token sha256"| C["Configurator: no password, recipe or truth"]
    C -->|"control endpoint: status, readings, call window, replacement, release"| P
    C -->|"assignments, gateway tools, prior notes"| W["Stage workers"]
    H -->|"after the run"| V["Evaluator in the harness: grades the frozen driver once"]
    V -->|"equivalence/1 with record_evaluation"| C
```

- **Every stage hands off.** It passes on its observed artifacts, their hashes and a hashed `notes.json` (`stage-notes/1`): the worker's own checks, including failed and not-run ones, the configurator's truth-free checks, dropped claims, tool refusals and open questions. A stage that produced nothing usable hands off empty with its notes, and the next stage starts. Generic emit receives the latest interpreted model that wrote a successful probe record, from probe or ground, with that record, and hands off only a package the configurator observed: one `emit_package` built in its assignment, hashed when the tool returned, or bytes it gave to `emit_check`; a worker report may name which package, never its hash. Benchmark emit hands off only a package `emit_package` built in its assignment, by the hash recorded when the tool returned, that passes `emit_check`: a package the worker wrote or changed is dropped with a note and never graded. Fresh reuse receives only the emitted package, the objective and permitted operating information, never notes.
- **Only safety, integrity, operator and host faults stop a run.** Safety covers effect grants, the reset rule, uncertain writes and binding conflicts. Integrity covers a recorded or observed hash that changed and a changed sealed input. Operator covers cancellation, budget, a runtime that cannot start and a missing binding. Host covers a crashed runtime or configurator; it is resumable. Worker report content never stops a run.
- **The device drives repair.** Differences between the model and what the configurator observed on its own device connection during probe or ground return to interpret within the repair budget, together with the defects the configurator's own validation finds in the assigned model (for an interface model, the runtime refuses such a model before it opens the device). Each probe record a stage hands on is bound in its notes to the model that wrote it, and a later stage compares a record with its assigned model only when that model wrote it; a record of a worker's own variant says nothing about the assigned model. The gateway reads the model of every device dispatch as the runtime does and refuses one its strict bounded reader cannot load, and an effectful operation of an interface model that fails validation, before it marks the dispatch uncertain; `probe_run` and `interface_execute` declare the checks they make before the transport opens (model bytes, validation, operation, sample count, evidence bound, replay fixture, and a register probe's binding, grants and a model the register runtime cannot load or drive) as refusals with `transport_open_attempted: false`, so none of these leaves an effect to reconcile; nor does a host fault a tool declares before contact. Probe and ground workers are not given `model_validate`, which may write beside the model it checks. When the budget is spent the run continues with the best revision.
- **One final verdict.** After reuse the run records `equivalence: {equivalent, basis, checks, diff}` once, as verdict `<run_id>:final`, and ends `completed` whether or not the driver is equivalent. A restart or resume never grades again, cancellation never replaces the completed status, and a sealing or cleanup failure after the verdict is recorded as an event without erasing it; an uncertain effect still blocks for safety. A generic run's verdict is labelled `self-evidence` and is not an independent grade. It is equivalent when the emitted package passed `emit_check` replay of the recorded device exchanges, every live operation of fresh reuse succeeded, and at least one of them ran the frozen package with `emit_test_live` on the configurator-supplied connection, including a function beyond its identity operation, that is an operation with a step that asks the device something identity's own steps do not, compared by what reaches the device (op and tx, and a USB control transfer's setup and requested length): identity alone is not evidence of function, nor is an operation that only waits or repeats identity's requests, however it reads or checks the reply. A replay is one of recorded device exchanges only when the package's probe evidence was recorded live; a replay of exchanges the worker supplied does not count, nor does a seeded package-versus-model check, which compares a package with its own model, not the device. The frozen package ran when the configurator hashed its bytes before dispatch and the snapshot the tool executed carries the frozen manifest. Fresh reuse is every reuse attempt that received the frozen package, including one that stopped and was resumed; each attempt's notes judge its live operations by the same rule. A call or operation refused before the device was contacted, as the runtime or the tool declares, is not a live operation; a host fault the tool declares before contact (such as a snapshot copy it cannot read back) is no refusal and leaves the verdict unscored, and any other toolchain error may have followed device contact and leaves it unscored too; a tool that cannot record what the device did still returns it. A host fault in the configurator's own `emit_check` stops the run for the host at emit, resumably, and never rejects the package. Only a named failure outside the package bytes is a host fault (a file or process failure around the check, such as reading back its own snapshot copy, or a replay process that ends without a result or cannot read the verified snapshot, an import, memory or a timeout); a package the worker wrote, however malformed, is rejected, including a register converter that will not load, and the check keeps its records outside the worker's workspace. When the operator's grants permit no function of the frozen package (each needs an effect that was not granted, or its channel resets the device on open and the reset was not granted, so its runtime refuses every operation), fresh reuse cannot test one and the verdict is unscored, not not equivalent. A package whose runtime needs the reset grant refuses a live probe of its bytes too, so its missing replay of device exchanges is that limit as well. So is it when the gateway refused every connection to the run's device for the operator or the host, from which no live probe could be recorded either: no device bound, or a serial device without a reset grant that was observed resetting on open or whose every listen failed for the operator, the host or the transport. These limits excuse only the one package that passed `emit_check` without a replay of device exchanges; no driver emitted, a candidate `emit_check` rejected offline, or several packages handed off is not equivalent whatever the device access. Listening needs no grant, so a serial device no worker listened to is the pipeline's own omission and excuses nothing. Reachability is judged by the run's binding state as of fresh reuse, so an operator observation recorded later never turns a refused connection into a verdict about the driver. A failure the runtime attributes to the driver after the device opened makes the run not equivalent when the operation ran the frozen bytes (the package, or its driver directory as a model); a failure of other bytes, an operator, host or transport fault, or a dispatch whose result was never recorded, leaves it unscored. A run stopped after fresh reuse resumes to finalize without a budget or device lease, since finalize contacts no device; a restart completes a benchmark run there awaiting its grade unless an effect is uncertain, and an uncertain effect on a run awaiting its grade blocks it for safety until the operator reconciles it and resumes. For a generic run, a host failure to read the frozen package at finalize stops the run for the host instead of grading the driver. A gateway call dispatches only while its assignment is the run's active one, and a stage is observed and committed only after every call of it has left the gateway.
- **Benchmark stages see no truth.** Benchmark runs are graded by the evaluator once, after the run, with basis `evaluator`. Every benchmark case, legacy tq9 and bme280 included, observes its stages without the evaluator or the truth: instrument readings of the emulated device are device evidence that workers see and nothing grades, the repair input is the device difference only (including the configurator's validation of an interpreted model the emulator cannot carry), and the run completes with `progress.equivalence = "pending"`.
- **Recovery.** At any stage, the provider's verified replacement of the emulator after a write the runtime attributed to the model commits with that stage's handoff, together with the replacement's session and binding, whose lease replaces the stopped emulator's; this resolves the write without re-executing it; the recovery uses a repair only when the stage's device difference revises, so a spent budget never refuses it, and a recovery that does not commit is recorded as failed and leaves the write uncertain. A write the frozen driver fails during fresh reuse is evidence about the driver: reuse's handoff advances and the driver is graded after the run.
- **The harness holds the password; the configurator holds none.** A bench harness, one detached process per trial, plays the operator. It receives the evaluator password file path on stdin and never writes it down, admits the case, takes the device recipe from the truth, starts and owns the emulator through a device provider built from that recipe alone, and starts the configurator run with the device descriptor, the admission evidence hash and the sha256 of a random evaluation token. It keeps the token sealed under the password in its trial directory with the truth envelope's key derivation, so a resume can unlock it and the configurator's hash reveals nothing about the password. The configurator holds no password, recipe or truth: it refuses password and emulator options, compares the admission hash with the public pin and the device image with the pinned image, and reaches the device only through the provider's control endpoint (status, readings, the paused-between-calls window, replacement and release). Live calls take turns: each takes an instrument reading before and after the call, which runs inside the window. A provider that cannot be reached before a call refuses it, leaving nothing uncertain, and the stage stops for the operator. The run releases the device when it ends, once no live call is inside the window; the harness stops it, confirmed, and concludes only a run it saw finish and whose handoffs it read.
- **One grade after the run.** For a completed run the harness then grades the frozen driver the run accepted once, on a fresh emulator of its own: the package of the latest emit handoff that handed one on, with the mapping of the probe whose model it packages, each re-hashed. It seals `benchmark-run-evidence/2` in its trial directory and posts the public `equivalence/1` record (check ids with passed flags and the failing ids with a reason; expected values, tolerances and raw records stay sealed) with `record_evaluation`. The configurator records it once as the run's final verdict, basis `evaluator`, only with the run's evaluation token and under its case's grading method, for a completed run with nothing uncertain, and only about the run's accepted emitted package; an identical repeat changes nothing and any other is refused. No package is `no-driver`, no mapping is not equivalent, and a changed record (including accepted bytes that changed before the seal), an evaluator host fault or a record the configurator's `equivalence/1` schema would refuse is `unscored`, an event that leaves the run awaiting its grade; `benchmark trial-resume` completes such a trial and never grades a final the evaluator's draft already holds. It refuses a password that does not unlock the trial's token before it grades, seals or posts anything. The frozen package is graded by its own model bytes. Only one evaluation of a trial runs at a time. A stopped run's handoffs are sealed alone.
- **Resume and readings.** A stopped run resumes a stage only on a device that answers, healthy, with the session and binding the run recorded; otherwise it stops for the operator until the harness attaches a verified device with its evaluation token (`attach_device`), which the configurator checks against the pinned image and the device's own status. Nothing grades a run before it is terminal. Readings leave the provider as `instrument-observation/1` values and units; its startup readings and recovery proofs stay in its private journal under the harness's bench home, beside the configurator home, and each emulator session's own files (its log, monitor commands it rejected) in a private directory there that is removed once the session's stop is confirmed; the run records the device's session, binding and recovery receipts.
- **Suites.** A suite is driven by a bench harness too. The configurator only freezes and stores it, with the sha256 of the harness's token, and settles each slot from the child's status and recorded verdict, which it reads itself; the harness reserves each slot, provides the child's device, has the configurator start or resume the child, grades its frozen driver after the run and posts the verdict. The configurator starts or resumes a child only while the suite runs and within its budget, under the suite's lock, so a cancelled or spent suite starts and resumes none, and only from the frozen slot's request plus what the harness adds (the device, its admission and the token hash); a child request, or a run recorded under the slot's request, that differs blocks the suite. The same start or resume sent again after a lost reply finds the child it started or resumed, whatever the suite did since, and the harness keeps that child's device until the child has stopped. A child advances the suite only with a graded or no-driver verdict; an unscored or pending grade and every stop block it, and the suite counts equivalent drivers out of those planned. Password files and the emulator executable reach the harness on its stdin, never the suite tables. A resume relaunches the harness, which takes the suite over with a token of its own, attaches a device anew to a stopped child (never while an effect is uncertain), with an approved extension of that child's budget if one is given, and grades an unscored one once. Suites frozen before this, with password files or no scheduler, are read-only.
- **Reports.** An assistive benchmark run reports as `benchmark-report/3`, whose success is its recorded verdict; `score` grades the single final sealed in the trial's `benchmark-run-evidence/2` again, after checking it graded the run's accepted emitted driver under the run's snapshot. An assistive suite report counts equivalent drivers out of those planned, lists unscored trials and counts stops by category. Reports of different protocols are never aggregated or compared.
- **Legacy cases.** Legacy cases follow the same split. A tq9 run runs on an emulator its harness starts from the legacy recipe (the sensor model, the Renode setup and the PWM registers its instrument reads as a duty fraction); started without that device, its start says so and its device stages stop for the operator. A bme280 run uses the operator's bound device, which its harness never touches: the harness authenticates the evaluator password against the case truth before the run starts and follows the run while the operator supplies the reuse reference and resumes it, through any budget extension; `benchmark trial-resume` grades a run that completed after its harness stopped following it. A device diff in its probe or ground sends it back to interpretation with that diff and the candidate it contradicts as sealed inputs. Both are graded once after the run from the fresh reuse the run recorded (method `recorded-reuse`): tq9 against its sealed reuse goal, bme280 against the operator reference within the truth's age and tolerance limits; reuse calls that failed for the host or the operator before the goal was observed, or a reference outside those limits, are `unscored`. No stage grades, records a stage verdict or ends a run with a frozen-final failure; runs recorded with that earlier terminal failure stay terminal.
- **Limits of this protocol.** Workers see instrument readings, which include firmware-internal state (such as parameter-store cells and the sampled sensor's latched reference), so assistive results are not comparable with a protocol whose workers see only the device's interface. Workers are not read-isolated until a real sandbox exists: a worker running as the same user can read files outside its workspace, including the device control endpoint file, with which it could act on the device outside the configurator's record. That exposes no truth; separation from the answer keys stays password-based. The provided emulator (v2 families and legacy tq9) runs only inside each live call, probe included, and is paused between calls; probe objectives tell workers so. The case manifests' `time_policy.probe` text ("continuous emulator virtual time") is part of the pinned case and stays unchanged; it is not the provided device's policy. Only a suite's harness attaches a device to a stopped run, so a stopped single trial is not continued, and a trial whose emulator stop was never confirmed is not graded, since no command yet records the operator's reconciliation of that emulator. Every change under `benchmark_support` changes the evaluator implementation, and the recorded calibration was already stale at `52eb018`: a fresh native calibration must precede the nine-trial end test, and sealed evidence of an earlier revision, the 2/3 series included, regrades only from a preserved checkout of that revision.
